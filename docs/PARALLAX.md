# Parallax downloads and private license desk

The original homepage, song page, stylesheet and music data are unchanged.
The new public page is `/parallax/`; owner access is `/parallax/admin/`.
There is no link to owner access on the public page. The admin HTML is a login
shell; every license generation request requires an authenticated server session.

Production is deployed on the existing `sustx-web` project:

- Downloads: https://www.sustx.xyz/parallax/
- Owner desk: https://www.sustx.xyz/parallax/admin/

The production secrets are already configured as sensitive Vercel
environment variables. They persist across deployments; normal code deployments
do not require recreating or uploading them again. Keep the existing local
credential files and plugin signing key. They are excluded from Git and the
deployment source upload.

## Local preview

Install `python3 -m pip install -r requirements.txt`, using a virtual environment
if your Python installation requires one. Then run:

```sh
python3 scripts/serve_parallax.py
```

Open `http://localhost:8080/parallax/` or
`http://localhost:8080/parallax/admin/`.
The preview server reads `.private/parallax-env.json` and blocks private files,
developer scripts and directory listings. Do not use a generic static server
from the project root after creating secrets.

Owner credentials have already been prepared in this checkout. The generated
owner password is in `.private/parallax-owner.txt`; put it in your password
manager. Nothing needs to be initialized again.

For a fresh checkout, first sync the release and restore the existing signing
key. Then prepare owner access (only if it does not already exist):

```sh
python3 scripts/setup_parallax.py --private-key ../vtex/.private/licensing/signing-key.pem
```

The command makes a random owner password and separate session secret. It checks
the signing identity against `parallax/release.json` before writing anything.
Local secret files have owner-only permissions and are excluded from Git and
Vercel deployment. Never put the signing key in HTML, JavaScript, or downloads.

## Deploy to the existing Vercel project

The project remains a static site, with one Python function at `/api/parallax`.
Use the existing `sustx-web` Vercel project and domain, with framework preset
**Other**, build command `python3 build_site.py`, and output directory `public`.
The build copies only public pages, assets and downloads; API source and private
storage never enter the static output. Python dependencies are
in `requirements.txt`. The installer files are served directly as static files;
they do not pass through the license function.

Before deploying, configure these sensitive server environment variables:

| Variable | Value |
| --- | --- |
| `PARALLAX_ADMIN_PASSWORD_HASH` | PBKDF2 hash generated by the setup script |
| `PARALLAX_SESSION_SECRET` | Random session signing secret generated by the setup script |
| `PARALLAX_SIGNING_KEY_BASE64` | Base64 of the existing private PEM, generated by the setup script |
| `BLOB_READ_WRITE_TOKEN` | Sensitive credential for the connected private customer-record store |

The values are in `.private/parallax-env.json`. Add them as **Sensitive** in
Vercel → project Settings → Environment Variables → Production. No client/public
prefix belongs on these names. Do not set `PARALLAX_LOCAL` in Vercel; that flag
is only for the local preview server, and is ignored when `VERCEL` is set.

Alternatively, with a signed-in Vercel CLI linked to the existing project:

```sh
vercel link
python3 scripts/setup_parallax.py --upload production
```

The upload command sends secrets through stdin and does not print them. It does
not publish the site. Review the linked project before uploading. Existing
variables are not automatically overwritten; change them in Settings if needed.
Deploy the reviewed changes using the existing Git integration or `vercel --prod`.
If using a preview deployment, configure its secrets separately with `--upload preview`.

Verify the original music pages, `/parallax/`, both installer downloads, and owner
login on the deployed domain. The license API stays unavailable until its secrets
are configured. Production sessions use Secure, HttpOnly, SameSite=Strict
cookies, expire after eight hours, and require a CSRF token and same-origin JSON
requests for issuing. Rotating the password hash or session secret invalidates
existing sessions. Use the generated random password; don't replace it with a
short PIN. Vercel Firewall can additionally rate-limit `/api/parallax` globally.

## Issue from your phone

1. Open `/parallax/admin/` on your site and sign in with the owner password.
2. Enter the customer's name and paste the complete request code they sent.
3. Tap **Generate license**.
4. Tap **Download license**, or **Share file** when your browser supports it.
5. Send the file to the customer; they choose **Import license…** in Parallax.

Only an authenticated owner can issue or read customer records. Each new license
is saved to the private `parallax-customer-records` Vercel Blob store before its
file is returned. Records survive redeployments and include customer, license ID,
computer code, platform, issue date, and the original signed file. Storage failures
prevent issuance instead of creating an unrecorded license.

The customer records panel supports search, repeat downloads and CSV export.
CSV exports contain metadata, with spreadsheet formulas escaped. To add licenses
issued before this feature, use **Import older license** with their original
`.parallax-license` files. Imports verify the production signature, preserve the
original file, and do not create duplicate entries. Conflicting files with the
same license ID are rejected.

These are **issued licenses**, not confirmed activations. The plugin activates
offline and sends no customer data to the website. No plugin update is needed.
There is no customer self-service issuing or email sending.

Production records are private blobs accessible only through the authenticated
API, never public download files or Git content. The store is connected to the
existing Vercel project for production; its credential is marked Sensitive.
Preview deployments need their own configured private store. Local previews use
`.private/parallax-records.sqlite3` (excluded from Git/deployment), or an explicit
`PARALLAX_RECORDS_PATH`; they do not change production records.

## Update a release

`vtex/VERSION.txt` remains the version source of truth. After building/package
creation in the plugin project, run:

```sh
python3 scripts/sync_parallax.py ../vtex
```

The script copies only the Mac installer, Windows installer and Windows VST3 ZIP,
then updates the public release manifest with version, size, SHA-256 and public
verification key. It never copies the private key. Downloads use versioned URLs
with immutable caching; reusing a version for a different binary is refused.
Keep older releases available if existing links need to continue working.

## Verification

```sh
python3 -m unittest discover -s tests -v
PARALLAX_NATIVE_VERIFIER=../vtex/build/license_tests python3 -m unittest discover -s tests -v
```

Tests use an unrelated deterministic test key. The second command also sends a
web-issued fixture through the real native plugin verifier. It does not read the
production private key or alter the locally saved plugin license.

The public download page currently offers only the Mac and Windows installers.
The Windows VST3 ZIP is retained among release artifacts for future use, without
a link on the public page.
